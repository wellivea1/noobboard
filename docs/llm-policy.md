# LLM Policy

LLM support is provider-based. The default provider is `disabled`, so the app does not fabricate diagnostic answers when no real provider is configured. Real providers are selected with `NOOBBOARD_LLM_PROVIDER=openai` or `NOOBBOARD_LLM_PROVIDER=anthropic`.

OpenAI API-key mode uses the Responses API with strict structured outputs. OpenAI ChatGPT connector mode follows the Codex/OpenCode-style OAuth pattern: an admin starts browser or device-code login, NoobBoard stores the returned refresh/access tokens as write-only local runtime settings, refreshes access tokens server-side, and sends diagnosis requests to the ChatGPT Codex responses endpoint with the saved account id. Browser login must use OpenAI's registered loopback callback (`http://localhost:1455/auth/callback`), so it only works when the admin page is opened as `localhost` on the NoobBoard host. LAN devices use the code login, which displays the OpenAI device code in the connection dialog and does not depend on a local redirect. Anthropic uses the Messages API with a forced client tool whose `input_schema` matches the diagnosis schema. All providers are called through Go `net/http`; no SDK or runtime dependency is required.

The `openai_model` setting is sent directly only in OpenAI API-key mode, where the default is the current flagship `gpt-5.5` and the settings UI offers current GPT-5.5/GPT-5.4-family options plus a small set of still-callable previous text models. The official OpenAI API model docs list GPT-5.5 and GPT-5.4 as Responses API models, and also list Codex-specific API models such as `gpt-5.3-codex`; that API model availability is not the same thing as ChatGPT-account connector support. ChatGPT connector mode therefore offers current GPT model names and does not offer `*-codex` slugs, because the ChatGPT-account Codex endpoint can reject Codex-specific model ids with "not supported when using Codex with a ChatGPT account." Blank, deprecated, or unsupported ChatGPT connector values are sent to the Codex endpoint as `gpt-5.5` with `reasoning.effort=high`, `store=false`, `stream=true`, and `include=["reasoning.encrypted_content"]` for stateless Responses continuation. If ChatGPT returns a 400 model-support error for the selected account, NoobBoard retries the request with the next configured GPT fallback. ChatGPT connector requests also carry the saved ChatGPT account id plus `originator` and per-request `session-id` headers, normalize the returned server-sent event stream before schema validation, and strip stored response item ids before feeding prior output back into the next request.

Environment variables:

- `OPENAI_API_KEY`
- `OPENAI_MODEL`
- `NOOBBOARD_OPENAI_AUTH_METHOD=api_key|chatgpt_browser|chatgpt_headless`
- `NOOBBOARD_CHATGPT_REFRESH_TOKEN`
- `NOOBBOARD_CHATGPT_ACCESS_TOKEN`
- `NOOBBOARD_CHATGPT_ACCOUNT_ID`
- `ANTHROPIC_API_KEY`
- `ANTHROPIC_MODEL`
- `NOOBBOARD_AGENT_AUTO_REPAIR_ENABLED=true|false`
- `NOOBBOARD_ACTION_AUTO_REVIEW_ENABLED=true|false`
- `NOOBBOARD_ACTION_AUTO_REVIEW_MODEL=same|openai/<model>|chatgpt/<model>|anthropic/<model>`
- `NOOBBOARD_ACTION_AUTO_REVIEW_REASONING=low|medium|high|xhigh`
- `NOOBBOARD_ACTION_AUTO_REVIEW_REFERENCES=docs/security.md,docs/llm-policy.md`

When `NOOBBOARD_LLM_PROVIDER=openai`, either `openai_auth_method=api_key` with `OPENAI_API_KEY` or `openai_auth_method=chatgpt_browser|chatgpt_headless` with saved ChatGPT connector tokens must be present. When `NOOBBOARD_LLM_PROVIDER=anthropic`, `ANTHROPIC_API_KEY` must be present. If the provider or matching credential is missing, the API reports diagnostics as unavailable and chat controls are disabled.

For OpenAI, the provider remains `openai`; `openai_auth_method` selects API key, ChatGPT browser login, or ChatGPT headless login. Settings reads return only booleans such as `openai_api_key_set` and `chatgpt_connected`; raw API keys, refresh tokens, access tokens, and account ids are never returned.

If OpenAI reports quota, billing, rate-limit, or usage-limit exhaustion, diagnose endpoints return HTTP `429` with `code=openai_usage_limit` and a plain message so the admin or compact chat UI can report the account limit clearly.

The LLM never receives raw credentials, unrestricted logs, arbitrary files, shell access, Docker control, arbitrary Unraid mutations, UniFi configuration mutation, or repair tools. The only storage mutation reachable from an LLM diagnosis is the narrow `ask_admin_to_start_array` path described below.

ChatGPT connector tokens are credentials. They are admin-only, audited on connect/clear, and must not be displayed, logged, sent to notifications, or included in LLM context.

Every diagnosis request collects a fresh NoobBoard snapshot from the configured collectors before building LLM context. In `live` or `mixed` integration mode, that means the LLM receives current read-only Unraid, UniFi, Docker, and probe status fields that pass role visibility and redaction. Context stays bounded by preserving valid JSON and progressively reducing duplicate or lower-priority detail before failing. Admin context first drops the duplicate raw snapshot, then shrinks selected app/log/fact/warning detail while keeping original app status counts. Compact/general-user context always uses a concise API report with source health and selected visible apps, prioritizing apps named in the user's question.

Admin-requested diagnosis enables read-only agent tools for live status lookups by default (`admin_requested.agent_tools_enabled=true`, `agent_max_tool_calls=2`). Existing runtime settings also re-enable the admin read-only tools when `agent_control_enabled=true`, so repair proposal mode and live status lookup do not drift apart. The browser/headless ChatGPT connector does not grant those tools by itself; it only supplies credentials. Tool access is controlled by `LLMPolicy.agent_tools_enabled`, `agent_max_tool_calls`, and `agent_tool_rules`, is denied for non-admin recipients, and is limited to these read-only tools:

- `noobboard_current_status`
- `noobboard_server_status`
- `noobboard_network_status`
- `noobboard_app_status`

Tool calls refresh sanitized NoobBoard snapshots through the normal collectors, then run role filtering and redaction before results are returned to the model. The tool loop has a hard call budget and fails closed on unknown tools, invalid arguments, collector errors, schema failures, or oversized/redaction-failed context. Mutating repair is not exposed as an LLM tool; app execution is a separate server-side repair path that maps one schema recommendation to a Docker start for stopped apps or Docker restart for non-stopped apps. General-user policies keep agent tools disabled.

The admin LLM settings response includes `agent_readiness` metadata for the UI. It reports read-only tool availability, restart-approval availability, the admin app-fix toggle state, the per-app cooldown/global repair limit, the safety-reviewer gate, and whether chat auto-fix can be offered. This metadata is not a permission source; every approval or automatic action is rechecked server-side.

Admin chat diagnosis responses also include derived `agent_plan` metadata. The model can only return a schema-allowlisted `recommended_action_id` plus a structured `recommended_action_target`. The server resolves the action ID through its own action registry, resolves app-specific targets against the current admin snapshot, and derives the concrete Docker action from that app state before creating the plan: stopped/exited apps use `start`, while non-stopped repair targets use `restart`. Unknown actions are normalized to a non-approval-eligible `unknown` plan, and app-specific actions with no exact target match become `target_unresolved`; neither case opens an approval dialog. Manual-check recommendations are shown as informational plan metadata and do not open an executable approval path. If the current snapshot reports the Unraid array as stopped, NoobBoard normalizes vague model answers to `ask_admin_to_start_array` and includes the admin-first guidance: contact the admin to confirm it was not intentionally stopped, but if the admin is unavailable or asleep and service needs to be restored, starting the array is okay. If the model returns `none`, `unknown`, or a generic admin-check recommendation while the current admin snapshot has exactly one down/degraded app with `agent_repair_allowed=true`, NoobBoard still surfaces a clearly labeled suggested app-fix plan. It is only a display reliability backstop; all approval and execution gates still run. When an approval-eligible action has the target information it needs, the frontend opens a normal Codex-style approval popup for the proposed fix unless the server already handled the plan through autonomous repair. The popup renders its selector from the server-provided `agent_plan.options` list so future action choices remain policy-driven rather than hardcoded in the browser.

Approval decisions use a short-lived server-signed plan token for the current plan ID, action ID, actor, resolved target, and replay nonce. `POST /api/admin/agent/approval` executes only the app-fix action behind `ask_admin_to_restart_container`, only when `agent_control_enabled=true`, only for a currently resolved, opted-in, non-blacklisted app, only once per token, and only within the repair limits (1/app/minute, 5/hour global). The server chooses Docker `start` for stopped/exited targets and Docker `restart` otherwise. Approval plans include the current cooldown policy and, when rate-limited, a retry countdown timestamp for the action popup. If `action_auto_review_enabled=true`, the approval endpoint first asks the selected reviewer model to validate the proposed app action against the current redacted admin snapshot and configured safe reference files. The reviewer selector supports `same` for the active diagnosis client, or explicit `openai/<model>`, `chatgpt/<model>`, and `anthropic/<model>` values. Reference loading is allowlisted to `docs/*`, `README.md`, and `AGENTS.md`, with byte limits and silent skips for missing files, so local secrets such as auth files cannot be sent as review context. Reviewer failures or denials fail closed and are audited before Docker is called. `POST /api/admin/agent/arm` is a legacy compatibility route and is not required by the current UI.

When `agent_control_enabled=true`, `action_auto_review_enabled=true`, and an admin diagnosis request includes `auto_repair:true`, the diagnosis may execute the same app-fix action automatically instead of opening the approval popup. Autonomous repair still runs only `ask_admin_to_restart_container`, only for a currently resolved app with `agent_repair_allowed=true`, only when the current app status is not `online`, only after reviewer approval, and only inside the shared cooldown/rate limit. The server chooses Docker `start` for stopped/exited targets and Docker `restart` otherwise. Reviewer failure or denial returns an `agent_plan` with the refusal status and does not call Docker. Successful auto repair clears approval controls from the plan, returns the verification `outcome` inline, and audits the `llm.agent_auto_repair.*` lifecycle plus the shared `app.container.action` event.

General-user diagnosis has a separate permanent auto-fix switch in app settings: `app_catalog.general_user_auto_repair_enabled`. General-user LLM context exposes only non-sensitive repair booleans (`restart_candidate`, `restart_allowed_general_user`, and `repair_requestable`) and keeps tools disabled. When the compact chat request includes `auto_repair:true`, a general-user diagnosis may auto-run the same server-side app-action path that backs the compact Start/Restart/Stop buttons, but only for an app already visible to that user and opted in with the standard-user app-control setting. The model still returns only the app-fix recommendation and target hint; if it misses the recommendation while exactly one visible app is down/degraded, NoobBoard may show a clearly labeled suggested repair affordance. The server chooses `start` for stopped apps and `restart` for non-online running apps. `stop` is never selected automatically. Separately, if NAS status is visible to the user's role and the current snapshot says the Unraid array is stopped, compact chat can show an LLM-only `Start array` prompt. That prompt carries a short-lived, one-use `execution_token`; `POST /api/user/agent/action` accepts only `choice:"start_array"` for `target_id:"unraid_array"`, re-checks that the array is still stopped, rate-limits the repair, calls only Unraid `array.setState(... START ...)`, verifies by refreshing status, and records infrastructure history. This action is not exposed as a normal manual compact control and is not run automatically by the auto-fix checkbox.

The admin Review Queue is only for explicit general-user repair requests. Successful compact direct controls and compact chat auto-fix actions are recorded as audit/history events and returned inline to the user; they should not add pending admin-review queue items.

After any repair execution, the server refreshes status several times, appends a repair outcome history event, returns an `outcome` object to chat, and does not auto-retry if the app is still down. Proposed, approved, auto-reviewed, executed, and verified lifecycle events are audited separately. Other approval-eligible recommendations are recorded as non-executing recommendations. Failures and refusals are audited and do not call Docker.

The app follows this flow:

Raw telemetry -> deterministic collectors -> diagnostic rule engine -> incident facts -> blacklist/redaction layer -> role-specific LLM context builder -> strict JSON diagnosis -> audit/notification pipeline.

OpenCode design note: OpenCode separates credential transport from tool authorization. Its OpenAI/Codex plugin handles OAuth/device-code tokens, while its permission and tool layers decide which tools are advertised and enforce checks again before side effects. NoobBoard follows that model with a narrower tool set. OpenCode also separates discovery (`websearch`) from retrieval (`webfetch`) and permission-gates both. If this dashboard ever gets web-backed research, it should be a separate admin-only feature with explicit source domains, audit entries, rate limits, and no access to raw private telemetry. Web access is intentionally not exposed in the current diagnostics path.

OpenCode auto-review package note: the referenced package is useful for review workflow design because it spawns a separate child review session, skips trivial or already-reviewed turns, and asks a different model family for a PASS/FAIL/UNKNOWN evidence checklist. NoobBoard copies the reviewer-model idea only as a fail-closed safety gate over concrete server-side app-action evidence. It does not copy OpenCode session review as a raw command-taking mechanism.
